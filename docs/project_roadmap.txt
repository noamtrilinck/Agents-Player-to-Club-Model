PROJECT OBJECTIVE
--------------------------------------------------------------------------------
Build a platform for football agents. An agent selects one of their players,
applies relevant conditions/filters, and receives the three most suitable
clubs in other countries for that player's next move.

The model must be based only on information we can actually derive from our
data. Do not introduce speculative concepts such as coaching preferences,
tactical intentions, transfer budgets, salaries, contract situations, or any
other information we do not currently have.


KEY ARCHITECTURAL DECISION
--------------------------------------------------------------------------------
This project reuses the validated player-evaluation framework already built
in National Team Selection (Ability scores, Attacking Philosophy/Profile
scores, Defensive scores, Competitive/context adjustments, and relevant
underlying player metrics) rather than re-deriving player quality from
scratch. See Stage 3.

The project's core, novel modelling challenge is learning club x position
player patterns from those player profiles, and then calculating how
compatible a candidate player's profile is with those patterns. See Stages
4-5.

The internal mathematical/statistical/ML calculations are never exposed to
the end user. The final user-facing output is eventually a simple:

    Match % + Explanation

"Complexity inside, simplicity outside."


DATA SOURCE
--------------------------------------------------------------------------------
The shared football data warehouse already exists at:

    Football Data/Data/database/database.db

This project reads from that database as its underlying raw data source. The
warehouse is not modified for project-specific logic — every project-specific
derived dataset or calculation lives inside this project's own production/
structure, never in the shared database.

This project does NOT automatically inherit the National Team Selection
project's scope rules, master dataset, or assumptions. Every scope decision
here (leagues, eligibility, minutes thresholds, goalkeeper handling, etc.)
must be made fresh, for this project's own objective.

Reusing National Team Selection's validated player-evaluation OUTPUTS (see
Stage 3) is a separate matter from inheriting its SCOPE — the two are not the
same decision, and one is not permission for the other.

Note: reusing National Team Selection's scores is not permission to move,
rewrite, or modify that project. It is documented here only as an intended
dependency, to be worked out concretely in Stage 3.

Architecture (restructured 2026-08-13 — see docs/stage2_agency_portfolio_mapping.md
for the full record): the canonical file is OUR ELIGIBLE-PLAYER UNIVERSE
enriched with agency information, not a list of Transfermarkt clients
enriched with matching information. Row count never changes during normal
processing — it is always exactly the Stage 1 universe. Processing an agency
means filling in the `agency` cell of that agency's matched players' EXISTING
rows; it never adds rows for agency clients outside our scope, and never
appends a second copy of a player.

Practical workflow (as implemented):

    Agency Transfermarkt portfolio page(s) -> extract clients -> match against
    our eligible-player universe (Stage 1) -> fill in the agency column for
    confidently matched players in the one canonical CSV

Update-in-place semantics: blank -> agency assigned (applied); same agency
already set -> no-op (idempotent rerun); a DIFFERENT agency already set ->
conflict, flagged for manual review, never silently overwritten. Verified
idempotent across all 29 processed agencies.

Matching rule: primarily NAME + AGE. Current club, position, and nationality
(all visible on the listing page) are supporting evidence only — a different
current club never blocks an otherwise-clear match, since our data and
Transfermarkt may reflect different points in time. Age is cross-checked
against our stored date_of_birth (not the coarser NTS "age" field), tolerant
of diacritics/transliteration/formatting differences in the name.

Individual Transfermarkt player pages are NOT part of the standard matching
workflow — only the agency's own client-listing pages are used, to keep
processing fast. Coverage is expected to be partial and highly league-
dependent (0% for agencies entirely outside our 33-league scope, up to ~30%
for agencies concentrated in leagues we cover) — expected, not a defect.

Uncertain/unmatched agency clients produce no row anywhere in the canonical
file — there is no place for them in a player-indexed table, and out-of-scope
Transfermarkt clients are deliberately excluded, not preserved.

This layer remains separate from player performance/scoring data — the
mapping CSV carries only identity fields, never Ability scores or metrics.

Canonical methodology: docs/stage4_canonical_methodology.md (read this, not any

A core modelling stage of this project.

The goal is NOT to claim we know a manager's tactical intentions, and — a
foundational correction made explicit on 2026-08-16 after Sprint 4.1 —
Stage 4 must NOT assume that the players a club currently fields at a
position represent what that club should recruit. A current Right Back may
reflect genuine system preference, squad availability, injury cover, a
recruitment limitation, or one of several equally valid archetypes.
Similarity to the incumbent is evidence, not the definition of fit.

Three separate questions, kept explicitly distinct throughout Stage 4 (never
combined prematurely):

  A. Observed Position Profile — "what types of players have actually
     played this position for this club?" Descriptive evidence only. Built
     in Sprint 4.2.
  B. System Compatibility — "given how this team plays, what player
     profiles are compatible with this position in this environment?" The
     central Stage 4 modelling question. May have more than one compatible
     archetype — the architecture must not force a single ideal vector if
     the evidence doesn't support one. Built in Sprint 4.5+.
  C. Squad Complementarity — "does a candidate add something the current
     positional options do not provide?" Distinct from System
     Compatibility: a player can be highly compatible with a team's
     football, dissimilar to the incumbent, AND highly complementary — a
     potentially excellent recommendation, not a contradiction. Explicitly
     NOT calculated in Sprint 4.2 or before; the architecture must simply
     preserve room to model it later, separately from System Compatibility
     and from incumbent similarity.

Basic modelling unit: Club x Position. Use the validated player-profile
dimensions from Stage 3 (never recalculated). Use the canonical club
universe (Stage 1's candidate_clubs.csv) and the canonical 11-position
taxonomy (NTS's position_taxonomy.py) — do not hardcode or redesign either.

================================================================================
DEVELOPMENT PRINCIPLES
================================================================================
1.  Build and approve one stage at a time. Do not implement later stages
    before the current stage has been reviewed and approved.
2.  Never invent unavailable data. If our database cannot support a
    variable, do not silently approximate it.
3.  Reuse validated player-evaluation work instead of rebuilding it
    unnecessarily.
4.  Do not assume that existing National Team Selection scope rules
    automatically apply to this project.
5.  Separate observable player patterns from claims about tactical
    intentions.
6.  Keep Club Pattern Learning (Stage 4) separate from Player-Club
    Compatibility (Stage 5).
7.  Keep Style Compatibility, Level Fit, and Squad Opportunity independent
    until each is validated.
8.  Do not lock final recommendation weights early.
9.  Use ML only where it provides measurable value over simpler methods.
10. Account explicitly for sample size and model reliability.
11. Keep technical calculations internal; provide simple user-facing
    outputs (Match % + explanation).
12. Preserve full traceability from every Match % back to its underlying
    model components.
13. Do not modify the shared warehouse for project-specific logic.
